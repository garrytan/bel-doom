# Plan: Doom in Bel at 640x480, at least 24 fps (stretch 80-100 fps)

Status: approved by Garry 2026-10-06 (autoplan gate). Author: Capy (Opus 5.5) for Garry Tan.

## Implementation plan

### Goal

Garry's target, unchanged: run the Bel Doom engine at **640x480 in the browser at >= 24 fps, ideally 80-100 fps**, without moving game logic out of Bel and keeping the engine purely functional (`tools/lint-idiom.mjs` clean).

Definitions (added in CEO review, both outside voices): **fps means distinct presented frames while gameplay runs at real-time speed (35 tics per second)**. Today the browser runs one tic per rendered frame, so 24 fps would mean the game runs at 69% speed, and nothing can exceed 35 fps. The plan therefore decouples simulation from rendering first. Frames above 35 per second require rendering between tics; this plan does that with pure interpolation in Bel, `(render (between w1 w2 a))`, as modern Doom source ports do.

### Where we are (measured on this 4-core cloud VM, Node 24)

| Resolution | Pixels | ms/frame (median) | step | render | write frame | Pairs per frame (env cells) | Live heap per engine |
|---|---|---|---|---|---|---|---|
| 160x100 | 16,000 | 41-54 | 3.5 | 50 | 0.6 | 776K (500K) | ~225 MB (780 MB RSS) |
| 320x200 | 64,000 | 128-178 | 5.2 | 154 | 3.6 | 2.07M (1.32M) | ~225 MB |
| 640x480 | 307,200 | fails today (status-bar scaling above 320 wide); extrapolated ~750 | | | ~17 (extrapolated) | ~10M | |

Acceptance machine (Garry's Mac, measured 2026-10-06): Apple M4 Max, 12 performance + 4 efficiency cores, 128 GB, Node 25, Chrome/Safari/Firefox. Engine-only in Node: 160x100 26.5 ms/frame (38 fps), 320x200 78.5 ms (13 fps), init 1.6 s, about 2x faster per core than the VM. 640x480 extrapolates to ~375 ms, so 24 fps there needs ~11x: roughly compiler 2x x pixel diet 1.5x x 6-8 render workers.

Profile at 320x200: GC 26%, interpreter call dispatch and variable lookup ~34%, native functions ~15%. The share each optimization removes is not yet measured, so speedups below are hypotheses to test, not commitments. 24 fps needs ~18x on this VM (750 ms to 41 ms).

### Ground rule: improve the interpreter, not the shortcut list (Garry, 2026-10-06)

No new jets during this run. Every speedup must come from the evaluator/compiler, from the engine's own Bel, or from the host. A second metric tracks how fast Bel code runs on PG's own definitions (`setJets(false)`): today `map` on PG's definition is 20x slower than its jet (interpretive overhead, which the compiler should shrink), `nth` 1,463x (no index cache), `rev` ~19,600x (PG's `rev` is O(n^2) by design: "I'm saying what append means, not trying to provide an efficient implementation"). Stage 1 reports the `map`-style interpretive gap before and after; algorithmic gaps are documented, not hidden.

### Stages (each is time-boxed and ends with a measured go/no-go)

Where the time goes at 320x200 (eng review, both voices measured): BSP walk ~2-3% of render, seg projection ~2%, wall and floor pixel generation ~45%, the rest of per-column work ~22%, sprites ~17%, weapon ~6%. About 11.7 pairs are allocated per pixel outside environments. So the work is per-pixel and per-column, and both the compiler and the pixel representation matter.

Budget per presented frame on one thread: `35 x step + fps x (render + write) <= 1000 ms`. With step ~3.5 ms, 24 fps leaves ~35 ms for render plus write, about 21x faster than today's extrapolated 640x480.

**Stage 0: correct timing, oracle, 640x480 correctness (time box 3 h).**
- Committed golden test in `test/` (not scratch): scripted multi-scene runs at 160x100 and 320x200 (combat, doors, death and respawn, damage and pickup tints, fences) hashing every output byte, run in separate processes per mode, plus a `BEL_NOCOMPILE` agreement run.
- Fixed 35 Hz simulation with one clock owner (the worker): per-tic input with tap consumption, `(doom-step w keys)` returning the next world and that tic's sound events, `(doom-render w)` writing the frame; up to 5 catch-up steps per presented frame, excess debt dropped and counted, pause when hidden. `doom-frame` stays as the composition for offline tools. `bin/doom-live.mjs` gets a per-tic script channel independent of frames. fps counts presented frames; a game-speed readout must show 35 tics/s.
- One immutable screen record (width, height, horizontal and vertical scale, integer source-pixel maps for pictures) built by `doom-init`, threaded through the existing view record `v` and destructured once per seg; resolution-dependent caches (sky tables, x-angles, HUD) keyed by it. 160x100 and 320x200 output byte-identical; tests for exact dimensions, edge pixels, sky and HUD alignment at 640x480.
- Bulk frame write (one jet-level write for the F packet).
- A slow single-worker 640x480 reference recording of the golden scenes.
- Credibility: the 160x100 golden reproduced with the closure tier and with jets off (PG's definitions; numbers and the native core macros still native, listed exactly); `?tier=closure` on the page; README's deviation list reconciled with `docs/interpreter.md`.
- Target hardware: Garry's Mac and browser measured when the paired device is reachable; otherwise no Mac projection.

**Stage 1: compiler tier (time box 6 h, gated).** Generic Bel-to-JavaScript compilation, scoped first to the forms the engine and bel.bel actually use, with everything else on the closure tier:
- Environments: a scope that contains a closure-creation point or a form handed back to the interpreter (`where`/place `set`, `dyn`, `after`, `ccc`, `def`, `mac`, `til`, `loop`, `(o x default)` and `(t x f)` parameters, `scope`) keeps a real alist built exactly as today (same cells, same order, shared by sibling closures). Only scopes with none of these use JS locals. Once an environment is reachable from Bel data it is only read through alist lookup.
- Macros are expanded at compile time behind per-use guards on the macro's identity and on the `nat` bits of the native core macros; a redefinition deoptimizes before the next use.
- JS-tier code is keyed by closure body plus static environment shape, never by a sub-pair (quasiquote can share one pair under two binders). Calls check that the closure's parameter list and body are still the compiled ones.
- The hot path: jets that call closures (`map`, `foldl`, `keep`, `sort`, `some`, `all`) and `applyF`/`applyT`/`compCall`/`ev` get a compiled entry that takes an argument array; the trampoline marker carries either (env, node) or (entry, args); self tail calls compile to loops.
- Inlined jets fall back to the real jet on anything unusual (so resumable `err` handlers behave identically); jet guards are checked per use; continuations and `after` pass through compiled frames; `dyn` invalidation fires when the binding is made and covers captured reads in existing closures.
- No Bel text in generated source (identifiers mangled, names in a side table, constants through an array); compile only bodies that have run hot; CSP refusal stays on the closure tier.
- Gate tests (committed): both tiers on basics, examples, bel.bel's definitions, a seeded shrinkable random-program generator, and the reflection matrix: `xdr`/`xar` on environment cells and spine through a closure list, sibling closures sharing one alist by `id`, `scope` via a macro, closure printing and `=` across tiers, a shared code pair under two binders, `(o ...)` defaults using earlier parameters, uvar parameters, a resumable `err` handler, `dyn` of a captured variable, macro redefinition after compile, where-mode through a compiled closure, mutated closure body.
- Go/no-go on measured end-to-end 320x200 render time with goldens equal: >= 1.8x continue; 1.3-1.8x continue only if Stage 2's diet is projected to close the gap; < 1.3x stop the tier and put the time into Stage 2.

**Stage 2: pixel representation diet and 320x200 at 35 fps (time box 3 h).**
- Cut the ~11.7 pairs per pixel: build each column once (no `column-pixels` appends of rebuilt runs, no `(map append tinted hud)` copy, tint applied while building), frame-local caches only.
- Checkpoint: 320x200 at 35 presented fps live at real-time speed on this VM (Doom's native mode), likely needing Stage 3 on 4 cores.

**Stage 3: parallel rendering, only if a gap remains (time box 4 h).**
- A full-width geometry pass first (BSP walk and projection, ~5% of render) produces the global visible-sector set and the masked-surface sort keys; workers then fill their column slices using those, so slicing cannot change which sprites appear or their order. Byte equality checked across several uneven and changing partitions, including fences overlapping sprites.
- Both designs hold the static level data in every worker (~225 MB live in Node per engine), so budget per-worker memory, free init-only data, and cap workers by measured heap (conservatively when `navigator.deviceMemory` is missing).
- Primitive-only render jobs keyed by (resolution generation, tic, interpolation sample, slice); bounded in-flight jobs, slice deadlines, stale-generation rejection, and fallback to one worker if a worker fails.

**Stage 4: above 35 fps (stretch, 320x200 first).** A pure render snapshot built from the last two worlds: thing positions by stable `id`, shortest-arc angles, camera height and door/lift heights interpolated; sprite frames, weapon state and animation from the newer world; no interpolation across respawns, teleports, spawns or removals; never fed back into `step`, never consumes randomness, never re-emits sounds (sounds come from every step). Interpolation turns off below 35 fps. At 640x480, 80-100 fps would need render in ~10 ms (about 70x today), so it is reported only if measured.

**Stage 5: ship.** Calibrate resolution after JIT warm-up (one re-init at most); the public page labels fallbacks. Live recordings, a dated performance chapter in the README backed by git timestamps, docs updated.

### Acceptance (640x480)

- >= 24 presented fps median and p95 frame time <= 60 ms over a 5-minute scripted run, with game speed 35 tics per second (+-1%), on the acceptance machine Garry chooses (see the approval gate).
- Output byte-identical to the slow single-worker 640x480 reference on the reference scenes.
- Peak memory within budget; input-to-present latency p50 under 100 ms (p95 reported).
- Measured on this VM and on Garry's Mac if reachable; 80-100 fps reported per machine.

### NOT in scope

- Moving any rendering or game logic to JavaScript, WebGL or WebGPU, or Doom-specific code in the compiler.
- WebAssembly backend (deferred).
- Exact rational numbers.
- New gameplay features.
- CI benchmark job (deferred).

#### 0A. Premise challenge

- **The real problem** is the demo's credibility and wow factor: 160x100 is chunky, and "it only runs at a quarter of Doom's resolution" is the obvious Hacker News objection. The direct metric is live fps at a given resolution in a normal browser, which the plan targets directly.
- **Premise: 640x480 is the right headline.** Partly. Doom's own native mode is 320x200 at 35 fps; hitting exactly that is the most authentic claim ("runs at Doom's native resolution and tic rate") and needs only ~5x, reachable after the compiler alone. 640x480 is above what Doom shipped with and is the stretch that impresses. Decision: add "320x200 at 35 fps" as an explicit milestone before 640x480 (accepted expansion, see below).
- **Premise: all three of compiler, allocation diet and workers are needed.** Yes by the numbers: without the compiler, workers and diet together give ~4x (750 ms to ~190 ms), far from 41 ms.
- **Premise: 80-100 fps is achievable.** Only on many-core machines. On this 4-core VM the projection is ~30 fps. The plan must report results per machine and not promise 80-100 fps everywhere.
- **Do-nothing cost:** nothing breaks; the project stays a 160x100 curiosity.

#### Sections 1-10

1. **Architecture.** New components: a JS-source compiler tier inside `interp/bel.js`; a pure `(render-slice world x0 x1)` in `doom/render.bel`; a worker pool in `web/`. Dependency graph:

```
  main thread (web/main.js)
     | keys per tic (broadcast, FIFO per worker)        frames slices (transferable)
     v                                                   ^
  worker 1..N (web/worker.js)  -- each: Bel interpreter + engine + identical world
     |                                                   |
     +-- (doom-frame-slice world keys x0 x1) --> step (pure, same on all) --> render-slice (pure)
                                   |
                       interp/bel.js: tier 2 (JS source) -> tier 1 (closures) -> ev
```
   Coupling added: the host must know slice boundaries; workers must agree on the world. Single point of failure: the slowest worker sets the frame time (tail latency). Rollback: `?workers=1&tier=closure` restores today's path at runtime; a revert of the compiler commit restores it in code.

2. **Error & rescue.** See the registry below. No silent failures: every fallback is counted and shown in the debug overlay.

3. **Security.** The compiler generates JavaScript with `new Function`. Threat: code injection through symbol names or literals. Mitigation: never splice Bel text into JS source; mangle identifiers to `v<N>` and pass all constants (symbols, strings, quoted lists) through a constants array. Threat: pages with a Content-Security-Policy that forbids eval. Mitigation: catch the failure and stay on the closure tier (GitHub Pages sets no such CSP). Likelihood low, impact low after mitigation.

4. **Data flow and edge cases.** Keys go to every worker in the same order (each worker's message queue is FIFO; the host stamps each message with its tic number and workers assert it). A worker that falls behind makes the host wait for its slice; the host never mixes slices from different tics (it stitches by tic number). Tab hidden: pause all workers. Resolution change: reload the page. Worker error: stop the pool, show the error, offer single-worker mode.

5. **Code quality.** The compiler tier lives beside the closure compiler with one entry point (`compileJS(closure)`) and an explicit list of supported forms; anything else returns null and stays on tier 1. Name generated identifiers for debugging (`/*bel:name*/` comments in generated source).

6. **Tests.** Equivalence is the core: run `test/basics.mjs`, `test/examples.mjs` and the engine golden hashes under both tiers; fuzz with random keys for 5,000 tics under tier 2; a worker determinism test (two engines in lockstep for 3,000 tics, world hashes equal); resolution screenshots at 160x100, 320x200, 640x480; live fps via `bin/doom-live.mjs` at each resolution. Hostile test: redefine `+` mid-run and check compiled code deoptimizes and the result changes accordingly.

7. **Performance.** Watch p95/p99 frame time, not just the median (GC pauses). Memory: each worker holds its own world and textures; measure heap per worker and cap N so total stays under ~1.5 GB. Startup: workers boot in parallel, so wall-clock init should stay ~4 s.

8. **Observability.** Debug overlay (E2) plus counters: closures compiled vs fell back, guard failures, pairs per frame (debug builds), worker lag in tics, desync count.

9. **Rollout.** Flags `?res=`, `?workers=`, `?tier=`; defaults chosen from measurements; ship as one PR per milestone so each can be reverted alone; GitHub Pages deploys on merge.

10. **Long-term trajectory.** Debt: a second compiler tier roughly doubles the interpreter's evaluation code; mitigated by the equivalence tests and docs. Reversibility 5/5 (flags). Platform potential: any Bel program gets faster, not just Doom.

### Phase 3: Eng review

#### Step 0: scope challenge, grounded in code

- **Timing.** `web/worker.js:46-56` calls `eng.frame(keys)` (one `doom-frame` = one `step` + one `render`) and reschedules with `setTimeout(step, 1000/TIC_RATE - elapsed)`. Decoupling needs two entry points, `(doom-step w keys)` returning the next world plus its sound events and `(doom-render w)` writing the frame packet, and a host loop that runs as many steps as wall-clock tics are due (capped at 5 per presented frame to avoid catch-up storms) and one render per presented frame. `doom-frame` stays as the composition of the two for the Node tools.
- **Resolution in the world.** 54 references to `screen-w`, `screen-h`, `view-h`, `half-w`, `half-h` and `focal` across `doom/*.bel`. `render` already threads a view record `v` (`render.bel:23-24`); the screen parameters join it, and the HUD and sky builders take them from the world. Horizontal and vertical scales split into `focal-x` and `focal-y` (equal at 160x100 and 320x200, so output stays identical; `focal-y = 1.2 * focal-x / 2` style correction only for square-pixel modes).
- **Escape analysis must be stricter than "captured by an inner function".** In Bel a closure's environment is the whole alist in scope when it is created, not just the variables it uses (`makeClo(a, ...)` in `interp/bel.js`). So `(car (cddr f))` exposes every enclosing variable, and `xdr` on any of those cells must be visible to the enclosing function. Rule adopted: a function body that creates no closures and does not mention `scope` keeps all its variables in JS locals; any variable in scope at a closure-creation point lives in a real `(var . value)` cell (one pair, shared by every closure and by the enclosing code); the alist spine over those cells is built lazily, once per closure, only when something reads the closure's environment or `scope`, and cached so its identity is stable. This still removes the spine allocation (half of the environment pairs) everywhere and all environment pairs in leaf functions.
- **Where/location mode, `dyn`, `ccc`, `after`, macros redefined at run time:** compiled bodies are not used for location mode; `ev` interprets the body with an environment materialized from the cells. A per-symbol `dynb` flip bumps a global generation; compiled functions check it on entry and fall back.
- **Complexity check.** The plan touches the interpreter (one new tier, ~600-900 lines), the engine (timing split, resolution threading, interpolation, allocation diet) and the host (loop, flags, overlay, optional pool). More than 8 files and more than one new module. This is a large change, so it is staged; each stage ships alone and has its own rollback flag.

#### Architecture

```
                          web/main.js (presentation, requestAnimationFrame)
                               |  keys (per tic, stamped)          ^ frame packets (transferable), stats
                               v                                   |
  web/worker.js  ---- scheduler: tics due = floor(elapsed * 35) - tic; run <= 5 steps; render once
       |
       |  (doom-step w keys) -> w'   [pure]        (doom-render w a) -> P/S/F bytes   [pure + one write]
       v                                                 |
  doom/game.bel step                         doom/render.bel render (BSP walk -> columns)
       |                                                 |   (between w1 w2 a) interpolation [Stage 4]
       +------------------------+------------------------+
                                |
                        interp/bel.js
          tier 2: Bel -> JS source (leaf locals, real cells, lazy spine, inlined jets, guards)
          tier 1: closure compiler (today)            ev: locations, dyn, ccc, after, fallbacks
          jets + CDR-coding cache + bulk frame write

  Stage 3 (only if needed): N workers, either replicated simulation (each worker steps the same keys)
  or one simulation worker sending a compact render state; the host stitches slices of the same tic.
```

New coupling: the host now owns the simulation clock; the engine exposes step and render separately. Justified: it is the only way to make fps mean presented frames at real-time speed.

#### Code quality
